# 引擎着色语言封装与转发机制分析

本文档基于 `data/` 下的 `.vs.c` / `.ps.c` 着色器源文件、`data/core/shaders/common/` 公共头，以及 `sdk/include/ig/material/Shader.h`、`sdk/include/ig/render/` 等头文件，推测引擎着色语言的封装方式与跨平台转发实现。

## 1. 结论先行：不是 Cg

**这套着色语言不是 NVIDIA Cg，而是引擎自定义的、基于宏的跨平台着色语言（Custom Shader DSL）**，其设计目标是**一份源码、三后端（D3D11/OpenGL/Vulkan）**。

判断依据：

| 特征 | Cg | 本引擎 | 结论 |
|------|----|----|------|
| 编译器 | `cgc.exe` 离线编译，运行期用 `cgCreateProgram` | SDK 头文件中**无任何 Cg API**（`cgCreate`/`cgCompile`/`cgc`/`NVFX_PROFILE` 全部未出现） | ✗ |
| 源码语法 | `struct`/`void main()`/`sampler2D`/Cg 标准库 | 宏包裹的 `ATTRI_BEGIN`/`MAIN_BEGIN_FRAGMENT`/`INIT_TEXTURE` | ✗ |
| 入口 | `main` | `MAIN_BEGIN_FRAGMENT(PS_OUT) ... MAIN_END` | ✗ |
| 跨平台 | 编译时按 profile 输出不同字节码 | 运行期 `#ifdef DIRECT3D11 \|\| OPENGL \|\| VULKAN` 分支 | ✗ |

引擎既不是 Cg，也不是直接的 HLSL/GLSL。它是一套**自研的宏驱动 DSL**，在编译/加载时被预处理展开为目标 API 的原生着色语言（HLSL / GLSL / SPIR-V）。

## 2. 着色器源码组织

### 2.1 文件类型

| 扩展名 | 形态 | 说明 |
|--------|------|------|
| `vs.c` | 纯文本（部分）/ 二进制（部分） | 顶点着色器源码（或预编译缓存） |
| `ps.c` | 纯文本（部分）/ 二进制（部分） | 像素/片段着色器源码（或预编译缓存） |
| `gs.c` | 同上 | 几何着色器 |
| `cs.c`（compute.h） | 同上 | 计算 shader |
| `*.h` | 纯文本（部分）/ 二进制（部分） | 公共头：`vs_base.h`、`ps_base.h`、`kit.h` 等 |

**重要观察**：同一目录下，部分 `.c`/`.h` 是明文源码，部分是二进制（带 `ac10` 魔数头部）。说明引擎支持两种形态：

- **明文源码**：开发态使用，引擎启动时预处理并编译
- **二进制缓存**：编译产物的缓存（`Shader::SetCachePath`/`GetCachePath`），加速下次启动

`Shader.h` 中 `sm_file_cache`（`jMap<jString, ShaderFile>`）即源文件缓存池，`ShaderFile::clone()` 返回内存源码副本。

### 2.3 一个典型片段着色器（`data/InfraRed/shaders/gauss/ps.c`）

```c
#include <data/core/shaders/common/ps_base.h>

    INIT_POSITION
    INIT_IN(float2, 0)
ATTRI_END

    float2 uv = IN_DATA(0);

    ...
    OUT_COLOR = color + float4(gauss, gauss, gauss, 0.0);
MAIN_END
#else
    #error unknown ps shader
#endif
```

## 3. 封装机制：宏驱动的跨平台 DSL

### 3.1 宏分类与作用

引擎通过四类宏把平台差异隐藏起来：

#### (1) 平台分支宏

```c
#ifdef DIRECT3D11 || OPENGL || VULKAN
    // 公共逻辑
#else
    #error unknown ps shader
#endif
```

`DIRECT3D11`/`OPENGL`/`VULKAN` 由 `Shader::loadFragment(name, defines)` 的 `defines` 参数注入，由各 API 后端在加载时设置。`data/core/shaders/common/platform/{dx11,gl,vk}.h` 提供平台差异定义。

#### (2) 输入输出声明宏

| 宏 | 作用 | 平台差异 |
|----|------|---------|
| `ATTRI_BEGIN(PS_IN)` | 声明输入结构体 | D3D11 → `struct PS_IN {`；GL/VK → `layout(location=x) in` |
| `ATTRI_END` | 结束结构体 | — |
| `INIT_POSITION` | 声明位置输入/输出 | D3D11 → `float4 position : SV_POSITION`；GL → `vec4 gl_FragCoord` |
| `INIT_IN(float2, 0)` | 声明第 0 个 varying 输入 | D3D11 → `float2 data0 : TEXCOORD0`；GL → `layout(location=0) in vec2 data0` |
| `INIT_OUT(float2, 0)` | 声明 varying 输出（VS） | 同上反向 |
| `INIT_COLOR(TYPE_RGBA)` | 声明像素输出 | D3D11 → `float4 color : SV_TARGET`；GL → `out vec4 color` |

#### (3) 资源声明宏

| 宏 | 作用 |
|----|------|
| `INIT_TEXTURE(slot, NAME)` | 声明 2D 纹理 + 采样器 |
| `INIT_TEXTURE_CUBE(slot, NAME)` | 立方体纹理 |
| `INIT_TEXTURE_SHADOW(slot, NAME)` | 阴影纹理（带比较采样器） |
| `INIT_TEXTURE_UINT(slot, NAME)` | uint 纹理 |
| `TEXTURE_NAME(NAME)` | 取纹理对象名 |
| `SAMPLER_NAME(NAME)` | 取采样器对象名 |
| `TEXTURE(tex, sampler, uv)` | 采样（封装 GLSL `texture()`/HLSL `Sample()`） |
| `TEXTURE_LEVEL(tex, sampler, uv, lod)` | 带 LOD 采样 |
| `TEXTURE_FETCH(tex, pos)` | `Load`/`texelFetch` |
| `GET_TEX_ID(NAME)` | 纹理 ID（用于 bindless/数组） |
| `CBUFFER_BEGIN(name)` / `CBUFFER_END` | 常量缓冲 |
| `UNIFORM type name;` | uniform 变量 |

#### (4) 入口与数据访问宏

| 宏 | 作用 |
|----|------|
| `MAIN_BEGIN_VERTEX(VS_OUT)` | VS 入口 |
| `MAIN_BEGIN_FRAGMENT(PS_OUT)` | PS 入口 |
| `MAIN_END` | 入口结束 |
| `IN_ATTRIBUTE(n)` | 取 VS 输入属性 |
| `IN_DATA(n)` | 取 PS varying 输入 |
| `OUT_POSITION` | 写位置输出 |
| `OUT_DATA(n)` | 写 varying 输出 |
| `OUT_COLOR` | 写像素颜色输出 |

### 3.2 内置变量与函数

源码中可直接使用以下"内置"符号，由 `ps_base.h`/`kit.h`/`shading.h` 提供：

- `s_viewport`、`s_imodelview`、`s_ambient_scale`、`Z_FAR` 等：由 `RExec::setShaderBaseParameter` 上传的引擎内置常量
- `float4`、`float3`、`float2`、`float4_one`、`float3_zero`：类型别名（兼容 HLSL 风格）
- `mul4(mat, vec)`、`lerp`、`srgbInv`、`discard`：数学/控制工具
- `GBufferDefault()`、`loadGBufferAlbedo(...)`、`dataCalculateAll(...)`、`getEnvironment()`、`checkMask(...)`：高级封装函数

这些符号让源码写法**更接近 HLSL**（`float4`、`mul`、`lerp`、`SV_POSITION`），便于从 HLSL 移植，但通过宏在 GL/Vulkan 下展开为对应 GLSL/SPIR-V 形式。

## 4. 转发机制：Shader 类与多后端

### 4.1 `Shader` 抽象基类（`sdk/include/ig/material/Shader.h`）

```cpp
class Shader : public Identifier<Shader>
{
public:
    enum {
        NUM_SHADERS = 6,                    // VS/Control/Eval/GS/PS/CS 六种
        VERTEX_MASK = 1<<0, FRAGMENT_MASK = 1<<4, COMPUTE_MASK = 1<<5,
        FLUSH_MASK = 1<<6,
    };
protected:
    struct ShaderFile { char* buf; char* data; int size; ... };
    static jMap<jString, ShaderFile> sm_file_cache;   // 源文件缓存
    jString m_name;
    jMap<jString, int> m_parameter_names;             // 参数名 → ID
    char m_parameter_id[NUM_FAST_ID];                 // 快速 ID 查表
    int m_flush_flags;
public:
    static void SetCachePath(const jString&);         // 设置编译缓存路径
    static void ClearCache();

    virtual bool loadVertex(const jString& name, const char* defines = 0);
    virtual bool loadFragment(const jString& name, const char* defines = 0);
    virtual bool loadCompute(const jString& name, const char* defines = 0);
    // ... Control/Evaluate/Geometry

    virtual bool loadVertexFromMemory(char* src, const char* defines, const jString& name, bool bPreprocess);
    virtual bool loadFragmentFromMemory(...);

    virtual bool compile() = 0;                       // 编译（纯虚）
    virtual bool compute(Texture* target, int gx, int gy, int gz) = 0;
    virtual void clear() = 0;
    virtual void release() = 0;

    virtual int findParameterID(const jString& name) = 0;
    virtual void setParameterFloat(int id, const float* v, int num) = 0;
    virtual void setParameterInt(int id, const int* v, int num) = 0;
    virtual void setParameterDouble(int id, const double* v, int num) = 0;
    virtual void setParameter(int id, const void* src, int size) = 0;
    virtual void flushParameters() {}
};
```

关键点：

- `loadVertex/loadFragment/loadCompute` 接受 `name`（源文件路径，如 `"data/core/shaders/render/scattering/vs_scattering_sample"`) 与 `defines`（预处理宏字符串，如 `"DIRECT3D11;SUN;SSAO"`）
- `bPreprocess=true` 表示引擎会先做宏展开（处理 `ATTRI_BEGIN`、`INIT_TEXTURE` 等），再交给底层 API 编译器
- `compile()` 是纯虚，由各 API 后端实现

### 4.2 多后端实现（推测）

虽然 SDK 公开头未直接暴露 `ShaderD3D11`/`ShaderGL`/`ShaderVulkan` 类，但从 `sdk/include/ig/render/{d3d11,opengl,vulkan}/` 子目录可推断存在对应后端：

| 后端 | `compile()` 内部行为 |
|------|---------------------|
| D3D11 | 宏展开后转译为 HLSL（`float4`/`SV_POSITION`/`SV_TARGET` 原生支持），调用 `D3DCompile` 编译为 DXBC |
| OpenGL | 宏展开后转译为 GLSL（`INIT_TEXTURE` → `uniform sampler2D;` + `layout(location)`），调用 `glShaderSource`/`glCompileShader` |
| Vulkan | 宏展开后转译为 GLSL，再经 `glslang`/`shaderc` 编为 SPIR-V，`VkShaderModule` 包装 |

预处理阶段统一由引擎完成（处理 `#include`、`ATTRI_BEGIN`/`MAIN_BEGIN_*` 等自定义宏），再交给各后端的原生编译器。

### 4.3 编译缓存

- `SetCachePath` 设置缓存目录
- `.c` 文件中带 `ac10` 魔数头的二进制文件即编译产物缓存，避免每次启动重复编译
- `sm_file_cache` 缓存源文件读入的 `ShaderFile`，避免重复 IO
- `NUM_FAST_ID=512` 的 `m_parameter_id` 数组用 hash 快速定位参数 ID，避免每帧字符串查找

## 5. 引擎侧的调用链

```
Material::load()                              // 材质加载
  └─ Shader::loadVertex(name, defines)        // 加载并预处理 VS
  └─ Shader::loadFragment(name, defines)      // 加载并预处理 PS
  └─ Shader::compile()                        // 后端编译
       ├─ D3D11: D3DCompile → DXBC
       ├─ GL:    glCompileShader → program
       └─ VK:    glslang → SPIR-V → VkShaderModule

RState::setShader(shader)                     // 绑定 shader
RState::setShaderParameterFloat(id, v, num)   // 设置参数（按 ID）
RExec::setShaderBaseParameter(is_screen)      // 设置引擎内置参数（s_viewport 等）
RExec::setShaderLightParameters(pass, lights) // 设置光照参数
RExec::setShaderTransformParameter(transform) // 设置矩阵
Shader::flushParameters()                     // 提交常量缓冲到 GPU
```

`defines` 参数在运行期由 `Render`/`Material` 根据当前配置注入：

- 平台宏：`DIRECT3D11` / `OPENGL` / `VULKAN`
- 功能开关：`SUN` / `MOON` / `SSAO` / `SSR` / `SSGI` / `LIGHTS` / `CLOUDS_SHADOW` / `TAA` / `DEBUG_ALBEDO` 等

例如 `composite_deferred/ps.c` 中的：

```c
#ifdef CLOUDS_SHADOW && SUN
    #include <data/core/shaders/cloud/common.h>
    INIT_TEXTURE(15, TEX_COVERAGE);
#endif
```

引擎在启用云阴影且存在太阳光时，向 `defines` 字符串追加 `CLOUDS_SHADOW;SUN`，触发该分支编译。

## 6. 设计评价

**优点**：

1. **单源多后端**：一份 `.c` 源码同时支持 D3D11/OpenGL/Vulkan，避免 HLSL/GLSL 双份维护
2. **平台宏集中差异**：纹理采样、IO 声明、入口签名等差异点封装在少量宏中
3. **HLSL 风格友好**：`float4`/`mul`/`SV_POSITION` 风格便于从 HLSL 移植
4. **运行期编译 + 缓存**：开发期可热改源码，发布期用缓存加速启动
5. **参数快速 ID**：`NUM_FAST_ID` hash 表优化每帧参数设置性能

**代价**：

1. 自定义 DSL 有学习曲线，IDE 无高亮/补全
2. 错误信息来自底层编译器（HLSL/GLSL/SPIR-V），定位源码行需对照展开后代码
3. 平台差异宏分散在 `common/platform/`，新增后端需同步扩展

---

## 7. 总结

引擎使用一套**自研的、宏驱动的跨平台着色 DSL**，而非 Cg。其核心机制为：

1. **源码**：`.vs.c`/`.ps.c` 纯文本，用 `ATTRI_BEGIN`/`MAIN_BEGIN_FRAGMENT`/`INIT_TEXTURE` 等宏声明 IO 与资源
2. **预处理**：`Shader::loadVertex/loadFragment` 读取源码到 `sm_file_cache`，按 `defines` 注入平台/功能宏，展开自定义宏为原生 HLSL/GLSL
3. **后端编译**：各 API 后端（D3D11/OpenGL/Vulkan）的 `Shader::compile()` 实现调用原生编译器，输出 DXBC/GLSL program/SPIR-V
4. **缓存**：编译产物以 `ac10` 头二进制缓存到 `SetCachePath` 指定目录，加速启动
5. **运行期**：`RState::setShader` 绑定，`setParameterFloat` 等按 ID 设置参数，`flushParameters` 提交

这种设计与现代引擎（如 Unity 的 ShaderLab、Unreal 的 USF/USH + Cross-Compiler）思路一致：上层用自定义 DSL 屏蔽平台差异，下层通过翻译 + 原生编译器生成目标字节码。

## 8. 与主流引擎着色方案对比

### 8.1 Unity ShaderLab

**形态**：声明式外壳 + 内嵌 HLSL/GLSL 代码块。

**结构**：一个 `.shader` 文件由两部分组成：

1. **`ShaderLab` 外壳**：声明式 DSL，描述属性、Pass、渲染状态、LOD、Tags 等元信息
2. **`CGPROGRAM ... ENDCG` 或 `HLSLPROGRAM ... ENDHLSL` 代码块**：内嵌原生 HLSL 风格代码

**示例**：

```shaderlab
Shader "Custom/Simple"
{
    Properties
    {
        _MainTex ("Texture", 2D) = "white" {}
        _Color ("Color", Color) = (1,1,1,1)
    }
    SubShader
    {
        Tags { "RenderType"="Opaque" "Queue"="Geometry" }
        LOD 100

        Pass
        {
            Name "Main"
            Tags { "LightMode" = "UniversalForward" }

            HLSLPROGRAM
            #pragma vertex vert
            #pragma fragment frag
            #pragma multi_compile _ _MAIN_LIGHT_SHADOWS
            #pragma multi_compile_fog

            #include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/Core.hlsl"

            CBUFFER_START(UnityPerMaterial)
                float4 _MainTex_ST;
                float4 _Color;
            CBUFFER_END

            struct Attributes
            {
                float4 positionOS : POSITION;
                float2 uv : TEXCOORD0;
            };

            struct Varyings
            {
                float4 positionCS : SV_POSITION;
                float2 uv : TEXCOORD0;
            };

            TEXTURE2D(_MainTex); SAMPLER(sampler_MainTex);

            Varyings vert(Attributes IN)
            {
                Varyings OUT;
                OUT.positionCS = TransformObjectToHClip(IN.positionOS.xyz);
                OUT.uv = IN.uv * _MainTex_ST.xy + _MainTex_ST.zw;
                return OUT;
            }

            half4 frag(Varyings IN) : SV_Target
            {
                half4 col = SAMPLE_TEXTURE2D(_MainTex, sampler_MainTex, IN.uv) * _Color;
                return col;
            }
            ENDHLSL
        }
    }
}
```

**跨平台机制**：

- **SRP（URP/HDRP）** 时代统一用 HLSL 代码块
- 编译期由 Unity 的 **Shader Compiler Pipeline** 翻译：
  - D3D11/D3D12/Xbox/PS：保留 HLSL，调 `D3DCompile` → DXBC/DXIL
  - OpenGL/GLES：HLSL → GLSL（经 `HLSLcc` 转译）
  - Vulkan/Metal：HLSL → SPIR-V（经 `glslang`），再 → MSL（Metal，经 `SPIRV-Cross`）
- **变体**：`#pragma multi_compile` / `shader_feature` 生成大量变体，由 **Shader Variant Collection** 预热
- **缓存**：编译结果缓存到 `Library/ShaderCache/`，以源码哈希为键

**与 EarthMaker 对比**：

| 维度 | Unity ShaderLab | EarthMaker DSL |
|------|-----------------|----------------|
| 外壳语言 | 自研声明式 `Shader { Properties {...} SubShader {...} Pass {...} }` | 无外壳，纯代码 `.c` 文件 |
| 代码块 | `HLSLPROGRAM ... ENDHLSL` 包裹原生 HLSL | `MAIN_BEGIN_FRAGMENT ... MAIN_END` 包裹宏化代码 |
| 属性声明 | `Properties { _MainTex("Tex",2D)="" }` 暴露到材质面板 | 通过 `.mat` 文件配置，不由 shader 声明 |
| 纹理声明 | `TEXTURE2D(_MainTex); SAMPLER(sampler_MainTex);` 宏（URP） | `INIT_TEXTURE(slot, NAME)` 宏 |
| 平台分支 | `#if defined(SHADER_API_D3D11)` / `UNITY_UV_STARTS_AT_TOP` 等 | `#ifdef DIRECT3D11 \|\| OPENGL \|\| VULKAN` |
| 变体管理 | `multi_compile` / `shader_feature` 自动展开 | 运行期 `defines` 字符串手动控制 |
| Pass 组织 | `.shader` 内多 `Pass` 块描述 | 引擎 C++ 代码（`RExec`）调度，shader 无 Pass 概念 |
| 编译目标 | DXBC/GLSL/SPIR-V/MSL | DXBC/GLSL/SPIR-V（无 Metal） |

**本质差异**：Unity 把"材质面板属性 + 渲染状态 + 多 Pass + 代码"全部塞进 `.shader` 一个文件；EarthMaker 把这些职责拆分——shader 只管代码，渲染状态由 `.mat` 管理，Pass 调度由 C++ 代码（`RExec`）控制。EarthMaker 更接近**纯 shader 代码**，无外壳层。

### 8.2 Unreal Engine USF/USH

**形态**：纯 HLSL 风格源文件 + 虚幻专属头文件 + 跨编译器（Cross-Compiler）。

**结构**：

- `.usf`（Unreal Shader File）：顶点/像素 shader 实现文件
- `.ush`（Unreal Shader Header）：公共头，类似 C++ 的 `.h`
- 材质图（Material Graph）：节点编辑器，编译时生成 HLSL 代码注入到模板 shader

**示例**（简化）：

```hlsl
// MyShader.usf
#include "/Engine/Private/Common.ush"
#include "/Engine/Private/PostProcessMaterialShared.ush"

void MainVS(
    in float4 InPosition : ATTRIBUTE0,
    in float2 InUV : ATTRIBUTE1,
    out float4 OutPosition : SV_POSITION,
    out float2 OutUV : TEXCOORD0)
{
    OutPosition = mul(InPosition, View.ProjectionMatrix);
    OutUV = InUV;
}

void MainPS(
    in float4 InPosition : SV_POSITION,
    in float2 InUV : TEXCOORD0,
    out float4 OutColor : SV_Target0)
{
    float3 color = Texture2DSample(PostProcessInput, PostProcessInputSampler, InUV).rgb;
    OutColor = float4(color * Intensity, 1.0);
}
```

**跨平台机制**：

Unreal 用自研 **Cross-Compiler**（`UnrealCrossCompiler`）：

1. **源码层**：统一写 HLSL 风格（`float4`、`mul`、`SV_POSITION`、`Texture2DSample`）
2. **D3D11/D3D12**：直接调 `D3DCompile` → DXBC
3. **OpenGL**：HLSL → GLSL（`HLSLcc` 自研转译器）
4. **Vulkan**：HLSL → GLSL → SPIR-V（或直接经 `glslang`）
5. **Metal**：HLSL → GLSL → SPIR-V → MSL（`SPIRV-Cross`）
6. **主机**（PS5/XSX）：各自原生 HLSL 编译器

**关键特性**：

- **`#include` 系统**：虚幻虚拟文件系统，`/Engine/Private/...` 路径映射到引擎 shader 目录
- **`View`/`ResolvedView`/`Primitive`/`Material` Uniform Buffer**：内置全局参数，自动绑定
- **`FMaterialPixelParameters`**：材质参数标准结构体，由材质图填充
- **变体**：`#pragma multi_compile` / `static const` 控制变体；Shader Permutation 大量预编译
- **虚拟纹理（VT）**：`VirtualTextureUniform.ush` 支持
- **缓存**：`Engine/DerivedDataCache/` 存编译产物，DDC（Derived Data Cache）系统管理

**与 EarthMaker 对比**：

| 维度 | Unreal USF/USH | EarthMaker DSL |
|------|-----------------|----------------|
| 源码风格 | 原生 HLSL（`Texture2DSample`/`SV_POSITION`） | 宏化代码（`TEXTURE()`/`OUT_POSITION`） |
| 头文件 | `.ush` + 虚拟路径 `/Engine/Private/` | `.h` + 相对路径 `data/core/shaders/common/` |
| 平台分支 | `#if COMPILER_HLSL` / `PLATFORM_WINDOWS` 等 | `#ifdef DIRECT3D11 \|\| OPENGL \|\| VULKAN` |
| 纹理采样 | `Texture2DSample(tex, sampler, uv)`（函数宏） | `TEXTURE(tex, sampler, uv)`（函数宏） |
| 全局参数 | `View.ViewToClip`、`Material.BaseColor`（UniformBuffer） | `s_viewport`、`s_imodelview`（cbuffer） |
| 变体管理 | `#pragma multi_compile` + Shader Permutation | 运行期 `defines` 字符串 |
| 材质图 | 节点编辑器 → 生成 HLSL → 注入模板 | 无材质图，`.mat` 文件配置 |
| 跨平台翻译 | `UnrealCrossCompiler`（HLSL→GLSL→SPIR-V→MSL） | 引擎预处理 + 各后端原生编译器 |
| 缓存 | DDC（Derived Data Cache） | `ac10` 魔数二进制 + `SetCachePath` |

**本质差异**：

1. **EarthMaker 比 Unreal 更"宏化"**：Unreal 保留接近原生 HLSL 的写法（`Texture2DSample` 是函数宏，`SV_POSITION` 直接用）；EarthMaker 几乎所有平台差异点都用宏包裹（`INIT_POSITION`、`MAIN_BEGIN_FRAGMENT`、`TEXTURE`）
2. **Unreal 有材质图**：节点编辑器是主力工作流，手写 USF 是辅助；EarthMaker 无材质图，全部手写 shader
3. **Unreal 的 Uniform Buffer 更结构化**：`View`/`Material`/`Primitive` 是命名结构体；EarthMaker 用零散的 `s_xxx` 变量
4. **跨编译器架构相似**：都是"HLSL 风格源码 → 翻译 → 多后端字节码"，但 Unreal 的 Cross-Compiler 更成熟（支持 Metal、主机）

### 8.3 三者综合对比

| 维度 | Unity ShaderLab | Unreal USF/USH | EarthMaker DSL |
|------|-----------------|-----------------|----------------|
| **外壳** | 声明式 `Shader{}` | 无（纯代码文件） | 无（纯代码文件） |
| **代码风格** | 内嵌 HLSL（`HLSLPROGRAM` 块） | 原生 HLSL | 宏化伪 HLSL |
| **IO 声明** | 原生 `struct` + 语义 | 原生 `struct` + 语义 | `ATTRI_BEGIN` + `INIT_POSITION` |
| **纹理** | `TEXTURE2D()` 宏（URP） | `Texture2DSample()` 宏 | `INIT_TEXTURE()` + `TEXTURE()` |
| **入口** | `#pragma vertex vert` | `void MainVS(...)` 函数名约定 | `MAIN_BEGIN_FRAGMENT(PS_OUT)` |
| **材质图** | ShaderGraph（可选） | Material Editor（主力） | 无 |
| **变体** | `multi_compile` | `multi_compile` + Shader Permutation | 运行期 `defines` 字符串 |
| **跨平台** | HLSL → 各后端 | HLSL → 各后端（含 Metal/主机） | 宏化源码 → 各后端 |
| **缓存** | `Library/ShaderCache/` | DDC | `ac10` 二进制 + `SetCachePath` |
| **成熟度** | 工业级，生态完善 | 工业级，跨平台最全 | 自研，覆盖 D3D11/GL/VK |

### 8.4 EarthMaker 的定位

EarthMaker 的着色方案可视为 **"Unreal USF 的简化版 + Unity 宏的集中化"**：

- **像 Unreal**：纯代码文件（无 ShaderLab 外壳）、HLSL 风格、`.ush`/`.h` 头文件体系、跨编译器思路
- **像 Unity URP**：用宏包裹纹理采样（`TEXTURE`/`SAMPLER_NAME` ↔ `TEXTURE2D`/`SAMPLER`）、IO 用宏声明
- **比两者都更"重"的宏化**：连入口签名都用宏（`MAIN_BEGIN_FRAGMENT`），而 Unity/Unreal 都保留原生 `void vert()`/`void MainVS()` 函数签名
- **缺失项**：无材质图、无 Metal 支持、无 DDC 级别的缓存系统

这套设计在**工程务实**上合理——以最小成本实现 D3D11/GL/VK 三后端统一，代价是牺牲了一些可读性和工具链完整性。对于 SDK 形态的引擎（供二次开发），宏化 DSL 的学习成本可接受，且源码透明度高，便于定位问题。
