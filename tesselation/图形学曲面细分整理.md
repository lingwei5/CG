## 1. 曲面细分的概念、原理与 OpenGL 实现

### 1.1 概念

**曲面细分（Tessellation）**是指：将一个由少量控制点构成的粗粒度图元（称为**补丁 / Patch**），在 GPU 上动态划分为大量更小的图元（三角形、四边形或线段）的技术。

$$
\text{Patch（低细节）} \xrightarrow{\ \text{固定功能细分器}\ } \text{大量细分顶点 + 小图元（高细节）}
$$

它的核心价值在于：

| 价值 | 说明 |
|------|------|
| **LOD（细节层次）** | 根据物体与相机的距离/屏幕占比，动态决定细分多少——近处多分、远处少分，节省几何量 |
| **位移映射（Displacement Mapping）** | 细分出足够密的顶点后，在 TES 中采样高度图做顶点位移，得到真实的凹凸几何（比法线贴图的"假凹凸"更真实） |
| **程序化曲面** | 在 TES 中直接对 Bezier / B 样条 / NURBS 曲面求值，以少量控制点表示光滑曲面 |
| **节省内存带宽** | 只传输少量控制点 + 细分等级，而不是海量三角形 |

历史沿革：细分最早在 OpenGL 4.0（2010）与 DirectX 11 中标准化。OpenGL ES 3.2 与 WebGL 2.0（通过扩展）亦支持。

### 1.2 原理：三个阶段接力

OpenGL 细分管线由**三个阶段**组成，中间夹着一段**固定功能硬件**：

```
顶点着色器 (VS)
    │  输出：控制点（gl_Position 等）
    ▼
① TCS 细分控制着色器（可编程，可选）          ←—— 决定"分多细"
    │  输出：新的控制点数组 + 细分等级（TessLevel）
    ▼
② 固定功能细分图元生成器（Tessellation Primitive Generator，纯硬件）
    │  依据 TCS 写入的内外细分等级 + TES 声明的域/间距模式，
    │  生成每个细分顶点的参数化坐标 gl_TessCoord，并装配出小图元
    ▼
③ TES 细分计算着色器（可编程，必需）          ←—— 决定"分出来的顶点长什么样"
    │  依据 gl_TessCoord 对控制点做插值/曲面求值，输出最终顶点位置
    ▼
几何着色器（可选）→ 裁剪/装配 → 光栅化
```

三阶段职责一句话概括：

- **TCS（Tessellation Control Shader，细分控制着色器）**：对每个 patch，输出（可修改的）控制点数组，并写入该 patch 的**细分等级**。它回答"这个 patch 要分多细"。
- **细分图元生成器（TPG，固定功能）**：完全不可编程。读取细分等级，在参数域（三角形/四边形/等值线域）内生成规则的细分坐标网格。
- **TES（Tessellation Evaluation Shader，细分计算/求值着色器）**：对 TPG 生成的每个细分顶点执行一次，用 `gl_TessCoord` 在控制点之间求值（插值或 Bezier 计算），输出真实空间中的顶点。

### 1.3 细分等级的含义（以四边形域为例）

- **外侧等级 `gl_TessLevelOuter[4]`**：控制四条边各被分成多少段。例如某条边等级为 $3$，则该边被均分为 3 段。
- **内侧等级 `gl_TessLevelInner[2]``**：控制内部沿两个方向各"嵌套"多少圈分割线。

三角形域只有 3 条外边（`Outer[0..2]` 有效）与 1 个内部等级（`Inner[0]` 有效）；等值线域只使用 `Outer[0]`、`Outer[1]`（以及等值线数量 `Outer[2]`，视 `isolines` 语义）。

细分生成的图元数量与等级近似呈平方关系。例如 quad 域：

$$
N_{\text{三角形}} \approx 2 \cdot (\text{Inner}_0 \times \text{Inner}_1)
$$

等级为 $64 \times 64$ 时一个 patch 就能生成约 8192 个三角形——这正是 LOD 控制如此重要的原因。

### 1.4 OpenGL 的实现方式

#### 1.4.1 输入

| 输入项 | 内容 |
|--------|------|
| 图元类型 | 绘制时必须使用 `GL_PATCHES`：`glDrawArrays(GL_PATCHES, first, count)` |
| Patch 大小 | 每个 patch 包含的控制点数 $n$（$1 \le n \le \text{GL_MAX_PATCH_VERTICES}$，通常上限 32） |
| 控制点数据 | 由 VS 处理后的顶点属性（`gl_Position` 及用户自定义 `out` 属性） |
| 细分等级 | 由 TCS 写入；若无 TCS，则使用应用程序设置的默认等级 |

#### 1.4.2 应用程序可控的参数（C++ API）

```cpp
// ① 每个 patch 包含几个控制点（这决定 TCS 被调用几次）
glPatchParameteri(GL_PATCH_VERTICES, 3);   // 例如：3 控制点 = 三次 Bezier

// ② 无 TCS 时的默认细分等级（仅在管线中没有 TCS 时生效）
GLfloat outer[4] = { 4.0f, 4.0f, 4.0f, 4.0f };
GLfloat inner[2] = { 4.0f, 4.0f };
glPatchParameterfv(GL_PATCH_DEFAULT_OUTER_LEVEL, outer);
glPatchParameterfv(GL_PATCH_DEFAULT_INNER_LEVEL, inner);

// ③（可选）用线框模式直观查看细分效果
glPolygonMode(GL_FRONT_AND_BACK, GL_LINE);
```

其余的"可控参数"**在 Shader 内部声明**，由 TES 的 layout 限定符指定：

```glsl
// TES 中的 layout 依次声明：域类型、间距模式、朝向、（可选）点模式
layout(quads, equal_spacing, ccw) in;
//     └域┘  └── 间距 ──┘  └朝向┘
```

| 类别 | 取值 | 含义 |
|------|------|------|
| **域（domain）** | `quads` | 四边形域，`gl_TessCoord` 为 $(u, v)$ |
| | `triangles` | 三角形域，`gl_TessCoord` 为重心坐标 $(u, v, w)$，$u+v+w=1$ |
| | `isolines` | 等值线域，画一批线段（头发、草、曲线） |
| **间距（spacing）** | `equal_spacing` | 边被等分为 $\lceil L \rceil$ 段，可能产生明显跳变 |
| | `fractional_even_spacing` | 分段数为 $\ge L$ 的最小偶数，边长用分数余量平滑过渡（LOD 切换时无跳变） |
| | `fractional_odd_spacing` | 同上，但取最小奇数 |
| **朝向（ordering）** | `ccw` / `cw` | 细分图元顶点绕序，影响背面剔除 |
| **点模式** | `points` | 只生成顶点不装配图元（用于把细分当"点云生成器"） |

#### 1.4.3 输出

| 阶段 | 输出 |
|------|------|
| TCS | 每个调用输出一个控制点（`gl_out[gl_InvocationID]` 及 patch 级 `out` 数组）；每个 patch 输出 `gl_TessLevelOuter[4]`、`gl_TessLevelInner[2]` |
| TPG | 细分顶点的参数坐标（供 TES 读取的 `gl_TessCoord`）+ 图元连接关系（进入图元装配） |
| TES | 每个调用输出一个最终顶点，**必须写入 `gl_Position`**（裁剪空间）；可附带任意用户插值属性 |

#### 1.4.4 最小可运行示例

```glsl
// ---- VS：直通 ----
#version 460 core
void main() {
    gl_Position = gl_ModelViewProjectionMatrix * gl_Vertex; // 实际项目中用自定义 uniform
}

// ---- TCS：控制细分等级（此处不改控制点）----
#version 460 core
layout(vertices = 3) out;   // 输出控制点数 = 本 TCS 每 patch 调用 3 次
void main() {
    gl_out[gl_InvocationID].gl_Position = gl_in[gl_InvocationID].gl_Position;
    if (gl_InvocationID == 0) {          // 细分等级只需（且只应）写一次
        gl_TessLevelOuter[0] = 4.0;
        gl_TessLevelOuter[1] = 4.0;
        gl_TessLevelOuter[2] = 4.0;
        gl_TessLevelInner[0] = 4.0;
    }
}

// ---- TES：在三角形域内做重心插值 ----
#version 460 core
layout(triangles, equal_spacing, ccw) in;
void main() {
    vec3 bc = gl_TessCoord;              // 重心坐标 (u, v, w)
    vec4 p = bc.x * gl_in[0].gl_Position
           + bc.y * gl_in[1].gl_Position
           + bc.z * gl_in[2].gl_Position;
    gl_Position = p;                      // 必须写入
}
```

> **注意**：C++ 端还需绑定 TCS/TES 到管线（`glAttachShader` + `glLinkProgram`，或使用 `glBindProgramPipeline` / separate programs），并保证 `GL_PATCH_VERTICES` 与实际顶点属性布局一致。

## 2. 细分控制 / 细分计算阶段：只写 C++ API 调用，还是必须写 Shader？

**结论先行：两个阶段都必须写 GLSL Shader（TCS 可省略但前提是接受默认细分等级），C++ API 调用本身不构成细分功能。**

### 2.1 各角色分工

| 角色 | 性质 | 是否必须写 |
|------|------|------------|
| C++ 应用侧 | 只负责**配置**：设置 patch 大小、（无 TCS 时的）默认细分等级、绑定着色器程序、以 `GL_PATCHES` 绘制 | 必须调 API，但仅靠它们不会发生任何细分 |
| **TCS** | **可编程**阶段（GLSL） | **可选**。省略时细分等级取 `GL_PATCH_DEFAULT_OUTER/INNER_LEVEL`，控制点直通（等同 TCS 恒等透传） |
| 细分图元生成器（TPG） | **固定功能硬件**，完全不可编程 | 不需要也无法写 |
| **TES** | **可编程**阶段（GLSL） | **必需**。只要管线里有 TCS 或想启用细分，就必须提供 TES；缺少 TES 时程序不完整（glLinkProgram 报错） |

### 2.2 为什么固定硬件不可编程、而两端可编程？

这种设计把职责拆得非常干净：

- "**分多细**"（细分等级）→ 数据驱动、随 LOD 动态变化 → 交给 **TCS** 可编程计算；
- "**怎么分**"（网格拓扑、坐标生成）→ 高度规则、纯数学 → 固化成 **TPG 硬件**，性能极高且实现统一；
- "**分出来长什么样**"（顶点位置、位移、法线）→ 任意多样（平面插值 / Bezier / 位移贴图）→ 交给 **TES** 可编程求值。

### 2.3 判断"什么时候只调 API 就够"

- **不需要动态细分等级、控制点无需修改** → 可以不写 TCS，仅设置：

```cpp
glPatchParameteri(GL_PATCH_VERTICES, 4);
glPatchParameterfv(GL_PATCH_DEFAULT_OUTER_LEVEL, ...);
glPatchParameterfv(GL_PATCH_DEFAULT_INNER_LEVEL, ...);
```

  但 TES 仍然必须写——否则顶点无从产生。

- **需要按距离/曲率/高度图决定细分等级、或修改控制点**（绝大多数真实项目）→ TCS 也必须写。

## 3. 细分相关内置变量总结

### 3.1 TCS 中可用

| 变量 | 类型 | 读写 | 含义 |
|------|------|------|------|
| `gl_in[]` | 块数组（含 `gl_Position` 等） | 读 | 当前 patch 的**输入**控制点数组，长度 = `gl_PatchVerticesIn` |
| `gl_out[]` | 块数组 | 写 | **输出**控制点数组，长度由 `layout(vertices = N) out` 指定（可 ≠ 输入数量！） |
| `gl_PatchVerticesIn` | `int` | 读 | 输入 patch 的控制点数量（即 `GL_PATCH_VERTICES` 的值） |
| `gl_InvocationID` | `int` | 读 | 当前调用在 patch 内的索引：$0 \le \text{id} < N_{\text{out}}$。TCS 每 patch 触发 $N_{\text{out}}$ 次调用 |
| `gl_TessLevelOuter[4]` | `float[]` | 写 | 外侧细分等级（写入后供 TPG 与 TES 使用） |
| `gl_TessLevelInner[2]` | `float[]` | 写 | 内侧细分等级 |
| `barrier()` | 函数 | — | 同步同 patch 的所有 TCS 调用（保证控制点/等级都已写完再继续），写完共享数据后、被他人读取前必须调用 |

**GLSL 声明上的关键细节**：用户自定义的 patch 级输出必须声明为数组，例如：

```glsl
layout(vertices = 3) out;
out vec3 vNormal[];   // 注意：必须是"无界数组"形式，长度隐式 = vertices
// 对应 TES 中：in vec3 vNormal[];   // 同样是无界数组，长度 = TCS 的 vertices
```

### 3.2 TES 中可用

| 变量 | 类型 | 读写 | 含义 |
|------|------|------|------|
| `gl_TessCoord` | `vec3` | 读 | 当前细分顶点在参数域中的坐标（本调用的"身份证"，见 3.4） |
| `gl_in[]` | 块数组 | 读 | 输入控制点数组（即 TCS 的 `gl_out[]`），长度 = TCS 输出的控制点数 |
| `gl_PatchVerticesIn` | `int` | 读 | 输入控制点数量 |
| `gl_TessLevelOuter[4]` | `float[]` | 读 | 细分等级（在 TCS 中是写，在 TES 中是读） |
| `gl_TessLevelInner[2]` | `float[]` | 读 | 同上 |
| `gl_Position` | `vec4` | 写 | 输出顶点位置，**必须写** |

> **TES 中没有 `gl_InvocationID`**（这一点是第 5 节讨论的关键，请务必记住）。

### 3.3 三个域中 `gl_TessCoord` 的语义

| 域 | gl_TessCoord 有效分量 | 几何意义 |
|----|----------------------|----------|
| `triangles` | $(u, v, w)$，且 $u+v+w=1$ | 三角形内一点的重心坐标 |
| `quads` | $(u, v)$（第三分量为 0） | 四边形内点的双线性参数，$u, v \in [0,1]$ |
| `isolines` | $(u, v)$ | $v$ 选择第几条线（沿 `Outer[2]` 计数），$u$ 是线上参数 $[0,1]$ |

### 3.4 `gl_TessLevelOuter` / `gl_TessLevelInner` / `gl_TessCoord` 三者关系图

```
TCS:  gl_TessLevelOuter / gl_TessLevelInner          (写入)
          │
          ▼
TPG:  依据等级划分参数域 → 为每个细分顶点算出 gl_TessCoord   (内部生成)
          │
          ▼
TES:  读 gl_TessCoord + gl_TessLevel* → 产出 gl_Position   (读取)
```

- `gl_TessLevel*` 描述"网格的密度"，是**每 patch 一组**的标量数组；
- `gl_TessCoord` 描述"我是网格中的哪一个点"，是**每细分顶点一个**的参数向量；
- 二者正交：等级决定有多少个 `gl_TessCoord` 被生成、以及它们落在域内的哪些位置。

### 3.5 变量速记口诀

| 变量 | 一句话 |
|------|--------|
| `gl_PatchVerticesIn` | 这个 patch 带了几个控制点进来 |
| `gl_InvocationID` | 我是这个 patch 内的第几个 TCS 调用（控制点编号） |
| `gl_TessLevelOuter/Inner` | 这个 patch 四边/内部各分几段 |
| `gl_TessCoord` | 我在 patch 参数域上的坐标（TES 专属） |
| `gl_in[] / gl_out[]` | 控制点的"进站口 / 出站口"数组 |

## 4. 为什么 gl_InvocationID 用来作为输入输出数组的索引？是因为细分着色器的输入单位是图元吗？

### 4.1 先修正一个理解：TCS 的"处理单位"与"执行粒度"

这个问题的回答需要先澄清两个不同层面的概念：

- **输入单位（数据组织单位）**：是 **patch（补丁）**。`GL_PATCHES` 是一种图元类型，一个 patch = $N$ 个控制点的打包整体。
- **执行粒度（每个 GPU 调用处理什么）**：TCS 的一个调用（invocation）**只处理 patch 中的一个控制点**，而不是整个 patch。

因此准确的说法是：

> **TCS 的输入单位是 patch（图元），但执行单位（每次调用的职责）是 patch 内的一个控制点。`gl_InvocationID` 是"当前调用负责第几个控制点"的编号，所以它天然就是输入/输出控制点数组的下标。**

所以："是因为输入单位是图元吗？"——**部分正确但不精确**。正确的因果链是：

1. 因为绘制类型是 `GL_PATCHES`（图元 = patch，内含多个控制点）；
2. 因为 GPU 并行模型要求把工作切分为"调用"，TCS 的工作被切成"每次调用一个控制点"；
3. 所以需要一个 patch 内的局部索引来区分"我是第几个控制点"——这就是 `gl_InvocationID`；
4. 因此读写控制点数组时用 `gl_in[gl_InvocationID]` / `gl_out[gl_InvocationID]` 是**职责对位**的自然结果。

### 4.2 为什么不一次调用处理整个 patch？（设计动机）

| 设计点 | 说明 |
|--------|------|
| 硬件并行友好 | TCS 常规工作（透传/变换控制点）是逐控制点独立的，切成调用后可像 VS 一样大规模并行 |
| 保持与 VS 相似的编程模型 | `gl_in[gl_InvocationID]` 对应 VS 中的 `gl_Position = ...`（一次一个顶点），学习成本低 |
| 又需要 patch 级信息 | 与 VS 不同，TCS **能看到整个 patch**（`gl_in[]` 全部可读），这是计算细分等级（曲率、包围盒等 patch 级决策）的前提 |
| 单写者原则 | patch 级共享数据（细分等级、patch 标志）不能多个调用同时乱写，于是约定通常由 `gl_InvocationID == 0` 的调用写一次，并用 `barrier()` 保证可见性 |

### 4.3 标准代码模式

```glsl
// 模式一：控制点直通/变换（每调用一个）
#version 460 core
layout(vertices = 3) out;
void main() {
    // 我只负责第 gl_InvocationID 个控制点的输出
    gl_out[gl_InvocationID].gl_Position = gl_in[gl_InvocationID].gl_Position;
    vColor[gl_InvocationID] = inColor[gl_InvocationID];

    // patch 级数据：只由 0 号调用写一次
    if (gl_InvocationID == 0) {
        gl_TessLevelOuter[0] = ...;
        gl_TessLevelInner[0] = ...;
    }
}
```

### 4.4 `gl_InvocationID` 的取值范围辨析（易错点）

`gl_InvocationID` 的上限是 **TCS 输出控制点数**（`layout(vertices = N) out` 的 $N$），而**不是**输入的 `gl_PatchVerticesIn`：

$$
0 \le \text{gl\_InvocationID} < N_{\text{out}}
$$

当 $N_{\text{out}} \ne N_{\text{in}}$（TCS 改变控制点数量，例如把 3 控制点 Bezier 升阶为 4 控制点）时：

- TCS 每 patch 调用 $N_{\text{out}}$ 次；
- 每次 `gl_InvocationID` 遍历 $[0, N_{\text{out}})$；
- 每个调用可以用任意方式从 `gl_in[0..N_{\text{in}})` 中取数据来构造第 `gl_InvocationID` 个输出点。

此时"数组下标 = 调用编号"的对应关系依然成立于 `gl_out` 侧；而 `gl_in` 侧则可以自由索引（见第 5 节）。

---

## 5. 为什么 TCS / TES 可以使用相同的索引？一个 TCS 调用严格对应一个 TES 调用吗？

### 5.1 结论先行

> **一个 TCS 调用绝不对应一个 TES 调用。二者的调用次数、触发时机、职责完全不同。**
>
> 它们之间唯一"相同"的东西是**控制点数组的下标空间**：TCS 写出的 `gl_out[i]` 逐元素地成为 TES 读到的 `gl_in[i]`。所谓"使用相同的索引"，指的是**数组下标 $i$ 在两个阶段指向同一个控制点**，而不是两个阶段的调用一一对应。

### 5.2 两个阶段的调用数量对比

以一个 patch 为单位（设 TCS 输出控制点数 $N$，细分后 TPG 生成 $M$ 个细分顶点）：

| | TCS | TES |
|---|-----|-----|
| 每 patch 调用次数 | $N$（= `layout(vertices=N) out`） | $M$（由细分等级决定，与 $N$ 无关） |
| 每次调用处理什么 | 一个**控制点** | 一个**细分生成的新顶点** |
| 区分调用的方式 | `gl_InvocationID`（patch 内局部索引） | `gl_TessCoord`（参数域坐标；**TES 没有 gl_InvocationID**） |
| 能看到什么数据 | 整个输入 patch `gl_in[0..N_in)` | 整个控制点数组 `gl_in[0..N)` |
| 输出什么 | `gl_out[gl_InvocationID]`（一个控制点）+ patch 级等级 | `gl_Position`（一个最终顶点） |

$$
\underbrace{\text{1 个 patch}}_{\text{图元}} \Rightarrow \underbrace{N \text{ 次 TCS 调用}}_{\text{每控制点一次}} \Rightarrow \underbrace{\text{TPG 硬件细分}}_{\text{固定功能}} \Rightarrow \underbrace{M \text{ 次 TES 调用}}_{\text{每细分顶点一次}}
$$

典型情形：3 控制点的三角形 patch、细分等级 4——TCS 调用 3 次，TES 调用约 $\frac{(4+1)(4+2)}{2}=15$ 次（三角形域等级 4 产生的顶点数）。$3 \ne 15$，对应关系显然不成立。

### 5.3 那"相同的索引"到底指什么？

用户产生这个疑问，通常来自如下成对出现的示例代码：

```glsl
// TCS：
layout(vertices = 3) out;
out vec3 vData[];
void main() {
    vData[gl_InvocationID] = ...;                    // 写：下标 = 控制点编号
    gl_out[gl_InvocationID].gl_Position = ...;
}

// TES：
layout(triangles, equal_spacing, ccw) in;
in vec3 vData[];
void main() {
    // 读：同样的下标空间 0,1,2 指向同样的三个控制点
    vec3 p = gl_TessCoord.x * vData[0]
           + gl_TessCoord.y * vData[1]
           + gl_TessCoord.z * vData[2];
    ...
}
```

正确理解：

1. **下标空间是同一个**：TCS 的每个输出数组（`gl_out[]` 与所有 patch 级 `out` 数组）在管线交接时**原封不动**地映射为 TES 的输入数组（`gl_in[]` 与对应的 `in` 数组）。数组的第 $i$ 个元素从 TCS 流向 TES 时仍是第 $i$ 个元素。
2. **因此 TES 中的 `gl_in[i]` 就是 TCS 中某次 `gl_InvocationID == i` 的调用写下的那个控制点**——"索引相同"指的是这一传递关系，而非"第 $i$ 次 TCS 调用对应第 $i$ 次 TES 调用"。
3. TES 访问这些数组时使用的是**常量下标 / 循环下标**（如三次 Bezier 的 0,1,2,3），与 TCS 中"用 `gl_InvocationID` 做下标"只是**恰好都可以用 0..N-1** 而已，本质原因是双方操作的**是同一份长度为 N 的数组**。

### 5.4 一个 TCS 调用严格对应一个 TES 调用吗？——否，且时间上还有 barrier 隔离

从执行时序看，二者甚至不在同一"批次"：

```
TCS 全部 N 个调用执行完毕
        │  （隐式 barrier：所有控制点与等级必须写完）
        ▼
TPG 读取等级，生成 M 个 gl_TessCoord 及图元连接
        │
        ▼
TES 执行 M 次（彼此并行，与 TCS 无任何调用级对应）
```

进一步的反例：

| 场景 | TCS 次数 | TES 次数 | 说明 |
|------|----------|----------|------|
| 控制点直通，等级 $(1,1)$ 三角形域 | 3 | 1 | 只生成中心一个点 |
| 控制点直通，等级 $(4,4)$ | 3 | 15 | 细分越密 TES 越多 |
| TCS 升阶 3→4 控制点 | **4** | 15 | TCS 次数由输出控制点数决定，甚至 ≠ 输入控制点数 |

### 5.5 概念对照总表

| 概念 | TCS | TES |
|------|-----|-----|
| 编程粒度 | 逐控制点（每 patch $N$ 次调用） | 逐细分顶点（每 patch $M$ 次调用） |
| 本次调用身份标识 | `gl_InvocationID` | `gl_TessCoord` |
| patch 身份 | 隐含（同一 patch 的调用并发执行） | 隐含 |
| 共享数据的写入 | `gl_InvocationID==0` 写等级 + `barrier()` | 只读 |
| 与对方调用的关系 | **无对应**（输出的是"配方/控制点"，TES 消费的是整份配方） | **无对应**（每次消费全部控制点） |

### 5.6 一句话总结

> TCS 与 TES 之间是**"生产配方"与"按配方做菜"**的关系：TCS 的 $N$ 次调用合力产出一份"配方"（$N$ 个控制点 + 细分等级）；TPG 依据配方决定要做出 $M$ 道菜；TES 的 $M$ 次调用各取**整份配方**、用自己的 `gl_TessCoord` 做出一道菜（一个顶点）。双方代码里"看起来相同的索引"只是同一份控制点数组的下标——它描述的是**数据**的对应，而不是**调用**的对应。

## 附：常见误区清单

| # | 误区 | 正解 |
|---|------|------|
| 1 | "细分等级在 C++ 里设置就够，不用写 shader" | C++ 的 `glPatchParameterfv` 只在**无 TCS** 时提供默认等级；TES 永远必须写 |
| 2 | "TCS 的执行单位是图元（patch）" | 输入单位是 patch，但**执行粒度是控制点**，`gl_InvocationID` 即控制点编号 |
| 3 | "gl_InvocationID 上限 = GL_PATCH_VERTICES" | 上限是 TCS **输出**控制点数 `layout(vertices=N) out` 的 $N$ |
| 4 | "TCS 第 i 次调用对应 TES 第 i 次调用" | 次数都不同（$N$ vs $M$）；TES 连 `gl_InvocationID` 都没有 |
| 5 | "TES 中也能写 gl_TessLevelOuter" | 在 TCS 中是写，在 TES 中是只读 |
| 6 | "细分等级只影响密度，不影响顶点位置" | TES 可以（且常需要）根据等级做 LOD 相关的偏移/位移强度调整，避免闪烁 |
| 7 | "quad 域的 gl_TessCoord 是 3D 重心坐标" | quad/isolines 是 $(u,v)$；只有 `triangles` 域是重心坐标 $(u,v,w)$，且 $u+v+w=1$ |
